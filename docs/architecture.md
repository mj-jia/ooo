# 架构与实现

页面没有构建步骤，三个文件直接以原生 ES module 运行：`index.html` + `src/style.css` + `src/app.js`，推理交给 `vendor/` 里预构建的 ONNX Runtime Web。

```
用户拖图
   ↓
createImageBitmap(file)         按 EXIF 方向解码
   ↓
prepareCanvases()               长边超上限则等比缩小，画到 cvBefore
   ↓
upscale()                       逐块推理，写进一张 ImageData
   ├─ 切块 256×256，每块多读 24 px 上下文
   ├─ 反射补边 → NCHW float32 张量
   ├─ sess.run() → [1,3,4h,4w]
   └─ 裁掉 96 px 边距，拷进目标位置
   ↓
（原图有透明通道时再按比例放大 alpha）
   ↓
canvas 显示 / 对比滑块 / toBlob 导出 PNG
```

## src/app.js 的四段

| 段落 | 职责 |
| --- | --- |
| 模型配置 `MODELS` | 每个模型的 url、输入输出节点名、体积标签、输入长边上限 |
| `ensureSession()` | 拉模型（带 Cache Storage）、建 `InferenceSession`、WebGPU 失败则回退 WASM |
| `upscale()` | 分块推理与拼接，纯计算，不碰 DOM |
| 事件与渲染 | 拖拽、滑块、进度条、下载 |

`upscale()` 与界面完全解耦，只接收 canvas、返回 `ImageData`。`tools/reference_run.py` 用 Python 复刻了同一套分块逻辑，两边结果可以逐像素对拍。

## 分块与拼接

整图一次推理会爆内存：一次 4 倍放大的特征图是输入的 16 倍像素、再乘通道数与 float32。所以切成 256×256：

```
每块实际推理的输入 = (256 + 24×2)² = 304×304
每块输出           = 1216×1216×3 float32 ≈ 17.7 MB
```

**为什么多读 24 像素**：卷积网络有感受野，块边缘的像素看不到块外的上下文，直接拼会产生网格状接缝。多给一圈上下文、算完再裁掉，接缝两侧就是同一份数据算出来的。

**边距怎么核**：`MARGIN = 24` 输入像素 → 输出 96 像素，裁剪时严格按 `MARGIN * SCALE` 对齐。这个倍数关系如果写错（比如按 1 倍裁），接缝会整体偏移，实测能做到 1 像素级错位都看得出来。

**越界怎么取**：图边缘的块，向外那 24 像素用镜像反射 `reflect(i, n)` 折回图内，而不是补 0 或补黑。补黑会让边缘变暗、出现暗框。

接缝验证方法：拼回的整图求相邻列的一阶差分，比较接缝列与周围列的差分均值。本项目实测接缝处的梯度落在图像自身纹理波动范围内，无可见断层。

## 内存上限来自哪

一个 1280×960 的输入，切 5×4 = 20 块，输出 `ImageData` 是 5120×3840×4 ≈ 78.6 MB，加上 canvas 备份与 alpha 蒙版，峰值接近 200 MB。移动端 Safari 大概率直接被杀。

所以两个模型各设了输入长边上限（均衡 1280 / 高质量 640）：**先把图缩到上限再放大**，而不是拒绝处理。副作用是「高质量」模式输出反而更小（640×4 = 2560），这是取舍不是 bug。

## 执行后端

```js
const tries = navigator.gpu ? [['webgpu', 'wasm'], ['wasm']] : [['wasm']];
```

按顺序尝试，第一个建 session 成功的就用它，失败自动降级。界面上「推理设备」一栏显示最终用的是哪个。

WASM 后端是**单线程**的：多线程需要 `SharedArrayBuffer`，需要 COOP/COEP 响应头，GitHub Pages 设不了。所以 WASM 下的速度就是单核速度，这也是优先 WebGPU 的原因。

## 模型缓存

用 Cache Storage（不是 HTTP 缓存），key 是模型 URL，仓库名 `upsr-model-v2`：

- 缓存命中直接 `arrayBuffer()`，不再走网络
- 下载是流式的，`content-length` 存在就显示百分比进度
- 换模型时若想强制失效，改缓存名里的版本号（`v2` → `v3`）

## 透明通道

模型只处理 RGB 三通道，alpha 由 canvas 双线性放大后逐像素写回：

```js
for (let i = 3; i < od.length; i += 4) od[i] = alphaData[i];
```

因此透明区域**不会被模型“补细节”**，只是等比放大。先扫一遍 `srcData` 的 alpha，全 255 就跳过这一步，省一次全图拷贝。

## 有意的取舍

| 取舍 | 原因 |
| --- | --- |
| 不做 Web Worker | ORT 的 wasm 后端本身不在主线程，额外 worker 收益小，却要复制 Input 数据、增加复杂度 |
| 每块 `await` 一次 setTimeout(0) | 让出主线程刷新进度条，否则大图会整页无响应 |
| 输出固定 PNG | 无损、支持 alpha；代价是文件大（5120×5120 可达二三十 MB） |
| 不内置超分倍数插值 | 2 倍模式是「4 倍后缩回」，质量优于直接 2 倍网络，但多花一倍算力 |
| 不引入打包器 | 无依赖树，原生 module 足够；改一行就能部署，也方便别人读懂 |
